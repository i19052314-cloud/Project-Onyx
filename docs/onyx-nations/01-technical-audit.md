## 3. Система Playerz: что известно и что недоступно

**Известно из README (документация):** Playerz — это NPC с ИИ-диалогом (текст Google
Gemini, голос Gemini Live), push-to-talk **N**, роли, отношения, телефонные звонки,
чат **T**, эмоции **F7**, визуальный контекст **Shift+L**, знания/сленг в
`Population/PhoneKnowledge/*.txt`, «мозги» контактов в `Population/Contacts/*.ini`
(имя, уровень, пол, модель, одежда, черты лица, любимое авто, статус мобильности).

**Недоступно:** исходников нет, публичного API/плагина нет, схемы сохранений нет.
Следовательно:

- программно создавать/управлять Playerz-персонажем,
- забирать деньги из кошелька Onyx,
- писать в сохранение Onyx,
- встраивать пункт в меню/телефон Onyx

— **всё это невозможно без либо (а) официального публичного API от правообладателя,
либо (б) реверс-инжиниринга, который запрещён политикой и лицензией.**

Практический вывод: население для NATIONS & WAR мы **управляем сами** (свои педы,
свои отношения, свои задачи), а не через Playerz. Сосуществование гарантируется тем,
что мы трогаем **только те entity, которые создали сами** (см. §6, правило владения).

## 4. Экономика и сохранения

- Onyx хранит настройки в `ProjectOnyx/Settings.xml`, прогресс — в `ProjectOnyx/Saves/`
  (в пакете их нет, создаются при первом запуске).
- Экономика игрока реализована (бизнесы, доходы, заказы, налоги через City Hall,
  штрафы, медицинские услуги).
- **Публичного контракта на чтение/запись этих данных нет.**

⇒ Наше расширение заводит **собственное сохранение** (`OnyxNations/Saves/`) и
**собственный бюджет государства**, независимый от кошелька игрока. Связь с деньгами
игрока — только опциональная, через настраиваемый мост (см. §7, уровень B).

## 5. Интерфейс и меню

**Как рисует UI сам Onyx:** собственный рисованный слой (прямоугольники, текст,
спрайты) поверх PNG-ассетов из `Assets/Menus`, `Assets/Phone`, `Assets/ThirdEye`,
`Assets/Hud`. Управление — свои горячие клавиши.

**Занятые клавиши (по README, трогать нельзя):** F9 (включить Onyx), F10 (настройки),
F7 (эмоции), N (push-to-talk), J, T, X, L, B, G, H, C, E, F, Shift+B, Shift+F, Shift+L,
0 (телефон), Tab, I (инвентарь), 1–5 (хотбар), Enter/Esc/Backspace/стрелки.
Свободными выглядят **F6, F5, F8, Ctrl+Alt-комбинации** — кандидат по умолчанию: **F6**
(планшет президента), переопределяется в нашем INI.

**GameStation 5 — единственный реально переиспользуемый UI-стек в этом репозитории:**
- `Console/web/index.html`, `shell.css`, `shell.js` (оболочка), `bridge.js` (API игр),
  `data/games.json` (56 КБ манифеста), 45 страниц игр, 91 SVG (art/hero), `vendor/three.min.js`.
- Архитектура: локальный HTTP-сервер внутри `GameStationHost.exe`
  (WinForms + `Microsoft.Web.WebView2`), страницы общаются с ним через
  **`GET/POST /api/save`**, `GET /data/games.json`; при открытии в обычном браузере
  есть фолбэк на `localStorage` — то есть оболочка **тестируема без GTA**.
- Вывод: этот паттерн (HTML-страница + JSON-манифест + `/api/save` + фолбэк) —
  готовая, проверенная модель для «президентского планшета».

**Ограничение:** `GameStationHost.exe` закрыт, и как именно Onyx его запускает/встраивает —
неизвестно. Поэтому для планшета есть два пути:

| Путь | Плюсы | Минусы |
|---|---|---|
| **A. Рисованный UI в SHVDN** (нативы `DRAW_RECT`/`DRAW_TEXT`/спрайты) — рекомендую | 0 зависимостей, 0 ассетов, работает в самом GTA, не конфликтует с Onyx, не требует браузера | верстать «руками»; текстовые таблицы |
| **B. HTML-планшет через свой хост WebView2** | красиво, тестируемо в браузере, стиль = GameStation | отдельный .exe-хост (WinForms + WebView2), IPC с GTA, риск фокуса/оверлея, дольше |
| **C. LemonUI / NativeUI (сторонние MIT-библиотеки для SHVDN3)** | готовые меню | внешняя зависимость, нужно подтвердить лицензию и версию под Legacy |

**Рекомендация: путь A как основной; макеты экранов можно параллельно держать в
`docs/onyx-nations/ui/` как HTML-превью (тестируются в браузере, в игру не идут).**
Так мы не ломаем UI Onyx (п.13 ТЗ) и не тащим ни одного нового бинарного ассета.

## 6. Ограничения GTA V Legacy / Native API (жёсткие)

Это самое важное для п.15 ТЗ. Проверено практикой SHVDN-модостроения, а не догадками:

| Ограничение | Следствие для архитектуры |
|---|---|
| Пул педов/машин лимитирован (зависит от gameconfig/HeapAdjuster). Безопасно держать **≈20–40 одновременно существующих модовых педов** и **≤15–25 машин** | Армия = **данные + спрайт-отряд**. Физически живы только отряды рядом с игроком |
| Дальний pathfinding нерабочий: `TASK_VEHICLE_DRIVE_TO_COORD_LONGRANGE` на >1–2 км по пересечёнке/воде не доезжает, «застревает», едет по дорогам не туда | Перемещение армий — **стратегический слой (данные)** с чекпоинтами; при приближении игрока — «материализация» отряда у ближайшего чекпоинта |
| Нет «армии» как сущности: бой = набор одиночных `TASK_COMBAT_*` с плохой групповой тактикой | Бой рядом с игроком: отряд 4–8 педов + связь через **relationship groups**. Бой вне экрана: **абстрактная формула** (сила×снабжение×мораль×местность + сид-рандом) |
| Нативные «флаги/КПП» есть лишь частично (`prop_flag_*`, `prop_barrier_work*`, шлагбаумы/башни — **нужна проверка имён в игре**) | Список пропов выносим в конфиг (`Props.xml`), каждый проп помечаем `Verified=true/false`; неверифицированные — отключены по умолчанию |
| Блипы: стабильно до ~100 | Карта государств рисуется **полигонами/маркерами только для ближайших регионов** + блип столицы/КПП по лимиту |
| Каждый тик SHVDN = кадр; тяжёлая работа в кадре = просадка FPS | **Планировщик интервалов** (см. ниже) + разбиение работы на чанки |
| Любая работа с несуществующим хендлом = вылет | Всегда `Exists()` перед нативом; весь тик в `try/catch` с логом в файл |
| Нельзя трогать чужие entity | **Правило владения:** модуль удаляет/изменяет только те педы/машины/блипы, которые создал сам и которые помечены в своём реестре |
| Диск в кадре = фриз | Сохранение — по триггеру/таймеру (≤ раз в 60 с и на `Aborted`/выходе), не в кадре |

**Планировщик (обязателен):**

| Система | Интервал |
|---|---|
| Ввод UI, отрисовка, отряды рядом (< 250 м) | каждый кадр / 100 мс |
| Отряды средней дальности (250–1200 м) | 500 мс |
| Стратегический слой (армии, фронты, бои вне экрана) | 2 000 мс |
| Регионы/контроль/границы | 5 000 мс (только при смещении игрока > 25 м) |
| ИИ государств-соперников (анализ угроз, решения) | 10 000 мс |
| Экономика (налоги, бюджет, инфляция) | 60 000 мс игрового времени |
| Дипломатия (переговоры, санкции, мир) | 30 000 мс |
| Автосохранение | 120 000 мс + по событию |

## 7. Что можно расширить: три уровня интеграции

### Уровень A — **Автономный модуль (можно делать сразу, 100% легально)**

Новый SHVDN3-скрипт `scripts/OnyxNations.dll` + папка `OnyxNations/`.
Использует **только** публичные API: GTA V natives + ScriptHookVDotNet.

- свои данные: `OnyxNations/Data/Nations.xml`, `Regions.xml`, `UnitTypes.xml`,
  `Cabinet.xml`, `Laws.xml`, `Diplomacy.xml`, `Props.xml`, `Bases.xml`;
- своё сохранение: `OnyxNations/Saves/world.json` + ротация бэкапов (5 шт.);
- свои NPC (педы/машины/блипы) с правилом владения;
- свой UI (рисованный) на **F6**;
- свой лог `OnyxNations/onyx-nations.log`.

Ничего из Onyx не читается, не меняется, не перехватывается ⇒ **совместимость и
обратная совместимость гарантированы**, удаление = удалить 2 папки/файла.

### Уровень B — **Мягкие мосты (опционально, выключены по умолчанию)**

Вещи, которые технически реализуемы без доступа к исходникам, но требуют осторожности:

- чтение/запись **денег игрока** через стандартные нативы статистики/кошелька
  (риск конфликта с экономикой Onyx — делать только через настройку
  `UsePlayerWallet=false` по умолчанию);
- уведомления — рисовать своим слоем поверх (не трогая слой Onyx);
- чтение позиции/состояния игрока — безопасно;
- **нельзя:** менять поведение Playerz, влезать в меню/телефон Onyx, писать в
  `ProjectOnyx/Saves/`, хукать ввод Onyx.

### Уровень C — **Глубокая интеграция (ЗАБЛОКИРОВАНО до письменного разрешения)**

- Playerz как граждане/министры/генералы;
- деньги Onyx как государственный бюджет;
- пункт меню/приложение в телефоне Onyx;
- запись в сохранение Onyx;
- нации внутри интерфейса Third Eye.

**Что нужно от правообладателя:** либо `AUTHORIZED_COLLABORATORS.md` с моим именем,
либо минимальный публичный контракт — например один статический класс-мост
(`OnyxApi.Player.Money`, `OnyxApi.Population.Spawn`, `OnyxApi.UI.Notify`,
`OnyxApi.Save.Register("OnyxNations", ...)`) + разрешение на разбор схем
`Data/*.xml`. Без этого уровень C физически невозможен без нарушения политики.

│   ├── Bases.xml                          базы, казармы, аэродромы, склады
│   ├── UnitTypes.xml                      пехота/мотострелки/танки/артиллерия/авиация/спецназ/ВП
│   ├── Cabinet.xml                        должности, кандидаты, компетенции

**Слои кода:**

1. **Core** — `TickScheduler` (интервалы), `Config` (XmlSerializer, валидация),
   `SaveSystem` (JSON + атомарная запись + бэкапы), `Log`, `Rand` (сид по миру).
2. **Sim** — *чистые данные, ни одного натива*: `Nation`, `Region`, `Army`, `Unit`,
   `Battle`, `Economy`, `Diplomacy`, `Government`, `Elections`, `AiNationBrain`.
   → Тестируется **вне GTA** (консольный харнесс): главный принцип п.17 ТЗ
   («механики важнее интерфейса») проверяется именно здесь.
3. **Presentation** — `EntityRegistry` (владение), `UnitSpawner` (LOD-материализация),
   `MapOverlay`, `TabletUI`, `Notifications`, `BorderProps`. Единственный слой с нативами.
4. **Bridge** — пустой интерфейс `IOnyxBridge` + `NullBridge` (уровень A) и
   `StubOnyxBridge` (уровень C, включается только когда появится официальный API).

**Модель «двух масштабов» (ключевая для п.7–9):**

- **Стратегический масштаб** (игрок далеко): отряд — это запись
  `{тип, численность, сила, боеприпасы, снабжение, мораль, координаты, приказ}`.
  Бои решаются формулой c сидом, результат детерминирован для того же сида ⇒
  воспроизводимость и тестируемость.
- **Тактический масштаб** (игрок ≤ 250 м): отряд **материализуется** — реальные педы,
  реальная техника, реальный бой через relationship groups, приказ
  «наступать/держать/отойти» превращается в_task-дерево. Игрок видит настоящие
  последствия, а не цифры в меню (п.17 ТЗ).

**ИИ государства-соперника (п.8, без заранее заданных сценариев):** утилитарная
модель. Каждые 10 с ИИ считает для каждого своего региона/границы вектор
угрозы: `threat = Σ(сила противника на направлении / расстояние × ценность региона × (1 − своя оборона))`,
затем выбирает действие с максимальной ожидаемой полезностью из набора
(усилить границу / контратаковать / захватить слабый регион / предложить мир /
ввести санкции / просить союза), учитывая бюджет, усталость от войны, рейтинг,
отношения с игроком и черты «личности» государства (агрессия, осторожность,
меркантильность — задаются в `Nations.xml`). Черты ≠ сценарий: это параметры
функции полезности, поведение emergent.

## 11. План реализации (15 шагов ТЗ → 8 milestones с критериями готовности)

Принцип: **каждый milestone заканчивается тем, что можно потрогать в игре**, а не
«написан класс».

| # | Milestone | Содержание | Критерий готовности (проверяемо) |
|---|---|---|---|
| **M0** | Каркас | Проект + конфиги/сохранение/лог/планировщик + пустой скрипт | DLL грузится, лог пишется, FPS не падает, Onyx работает как раньше |
| **M1** | Государства и карта | `Nations.xml`, `Regions.xml`, определение региона по позиции, 2 государства | В игре у каждого региона корректный владелец; смена владельца сохраняется и переживает перезапуск |
| **M2** | Границы и КПП | `Borders.xml`, пропы, пограничники, реакция NPC на пересечение | Пересечение границы → реакция пограничника + уведомление; FPS стабилен |
| **M3** | Президент + выборы | Кампания, рейтинг, инаугурация, срок, переизбрание | Игрок реально становится президентом, рейтинг меняется от решений, результат сохраняется |
| **M4** | Правительство | 7 министров, назначение/увольнение, компетенции, поручения и отчёты | Назначенный министр меняет соответствующий показатель; отчёт приходит |
| **M5** | Армия (стратегия) | Юниты как данные, базы, мобилизация, приказы, перемещение | Приказ «наступать» → юнит реально движется по карте (видно на карте операций) |
| **M6** | Армия (тактика) | Материализация отрядов рядом, relationship groups, бой | На глазах у игрока отряд едет/идёт и вступает в бой; удаление при отдалении |
| **M7** | Война и захват | Объявление войны, бои вне экрана, захват/оккупация/освобождение, флаг | Захваченный регион меняет владельца, ставится флаг, сохраняется после перезапуска |
| **M8** | ИИ-соперник, экономика, дипломатия, полиция | Утилитарный ИИ, бюджет/налоги, союзы/санкции/мир, новости | Соперник сам атакует и предлагает мир; налоги меняют настроение и бюджет; всё сохраняется |

**Полировка (после M8):** баланс, производительность, документация, установщик.

**Порядок именно такой**, потому что M1–M2 дают «мир», M3–M4 — «роль игрока»,
M5–M7 — «армия действительно воюет» (п.17), M8 — «второй разумный актор».
Менять местами M5 и M6 нельзя: тактика без стратегии = тысяча педов = вылет.

## 12. Честные ограничения будущего продукта

1. **Армии — не тысячи.** Возле игрока одновременно живёт ограниченное число отрядов;
   остальное — числа. «Парад из 200 солдат» в GTA V Legacy стабильно не сделать.
2. **Дальние боя абстрактны.** Победа считается формулой, а не симуляцией — но с
   реальными последствиями (владелец, разрушения, настроение, бюджет).
3. **Playerz не станут гражданами** без официального API (уровень C).
4. **Деньги игрока ≠ бюджет государства** по умолчанию (уровень B выключен).
5. **Пропы (флаги/шлагбаумы/вышки)** требуют проверки имён моделей в игре; до проверки
   они `Verified=false` и отключены — обещаю не выдавать непроверенное за готовое (п.2 ТЗ).

для уровня C, но не *техническое* — исходного кода ядра Onyx в этом репозитории

реализуется только через `Bridge/IOnyxBridge.cs`, и до появления контракта там
стоит `NullBridge`. Как только появится API или исходники ядра — мост
реализуется без переделки остального кода: именно для этого шов и оставлен.
